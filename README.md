# ESP32-C6 Clock + Weather ⏰🌡️

Настольные Wi-Fi-часы с большим OLED SSD1322 256×64 **и** метеостанцией на BMP280.
Одна плата **Waveshare ESP32-C6-Zero**, живой веб-дашборд, REST API, WebSocket, MQTT/Home Assistant.

Объединение двух проектов: `esp32-clock` + `esp32_zigbee_temperature`.

---

## ✨ Возможности

**Часы**

- Крупное время `HH:MM` и температура на одном экране, разделённые вертикальной чертой
- Автоматический переход зима/лето по POSIX-`TZ`, ре-синхронизация NTP раз в 6 часов
- Авто-яркость по времени суток, ручная регулировка, полное отключение экрана
- Секундомер `MM:SS.mmm`, после 60 минут → `HH:MM:SS`, круги (laps) в браузере
- Отсчёт на OLED и в браузере идёт синхронно с компенсацией сетевой задержки — см. раздел «Секундомер» ниже

**Метео**

- Температура, давление (гПа / мм рт. ст.), высота, QNH, плотность воздуха
- Тренд давления и простой прогноз (☀️ / ⛅ / 🌧️)
- Мониторинг батареи 18650 (делитель + кривая разряда Li-ion)

**Сеть и интеграции**

- Веб-дашборд с live-обновлением по WebSocket, светлая/тёмная тема, сворачиваемые блоки
- REST API + WebSocket, доступ по `http://clock.local` (mDNS)
- MQTT + Home Assistant Discovery → отсюда же в **Apple Home** (см. ниже)
- WS2812 статус-индикация, авто-реконнект Wi-Fi

> OTA в проекте нет: она была убрана, и освободившийся второй app-слот отдан под один
> раздел на 3 МБ (см. [Разделы и флеш](#разделы-и-флеш)). Прошивка — по USB.

## 📌 Распиновка

Используются **только боковые гребёнки**. Пины `6, 7, 8, 9, 12, 13, 23` на них не выведены — они в нижнем торцевом ряду, для проводного монтажа неудобны.

```text
        ESP32-C6-Zero
   ЛЕВАЯ                ПРАВАЯ
   5V                   TX (16)
   GND  ← дисплей 1     RX (17)
   3V3  ← дисплей 2,12  14
   0                    15
   1                    18 → дисплей 4  (CLK)
   2    → батарея ADC   19 → дисплей 5  (DIN)
   3                    20 → дисплей 14 (DC)
   4    → BMP280 SDA    21 → дисплей 15 (RST)
   5    → BMP280 SCL    22 → дисплей 16 (CS)
```

OLED разведён на правый ряд одним шлейфом: SPI — самые быстрые линии в схеме, тянуть их с изнанки платы не стоит. Слева остаются BMP280 (4, 5) и батарея (2).

Свободный резерв: `0, 1, 3, 14, 15` на гребёнках. Все пины меняются в `src/config.h`.

### Дисплей SSD1322 (16 контактов)

На плате модуля контакты просто пронумерованы 1…16.

| Пин | Сигнал | Куда |
| --- | --- | --- |
| 1 | GND | **GND** |
| 2 | VCC | **3V3** |
| 3 | NC | **NC** |
| 4 | SCLK | **GPIO18** |
| 5 | SDIN | **GPIO19** |
| 6–11 | D2–D7 | **GND** |
| 12 | RD# | **3V3** (вместе с пином 2) |
| 13 | WR# | **GND** |
| 14 | D/C | **GPIO20** |
| 15 | RST | **GPIO21** |
| 16 | CS | **GPIO22** |

> **Почему 6–13 не бросают в воздух.** Это линии параллельной шины, в режиме 4-wire SPI они не используются, но даташит SSD1322 требует задавать неиспользуемым входам определённый уровень. `RD#` активен низким уровнем, поэтому его держат на плюсе (неактивное состояние), остальные — на земле.

### Перемычки режима интерфейса

На обороте модуля напечатана таблица `R5 R6 R7 R8` со строками `3SPI / 4SPI / 80XX / 68XX`.
Нужен режим **4SPI**: запаяны **R5 и R8**, позиции R6 и R7 — пустые (BS1=0, BS0=0).
Если модуль в параллельном режиме или 3SPI — экран просто останется тёмным без ошибок в логе.

### Прочее

| Узел | Пин | Примечание |
| --- | --- | --- |
| BMP280 SDA / SCL | GPIO4 / GPIO5 | Strapping-пины, но для I²C безопасно: подтяжки модуля тянут вверх, что совпадает с состоянием при загрузке |
| Батарея (делитель) | GPIO2 | ADC1_CH2. Схема: `BAT+ ──[100к]──●──[100к]── GND`, точка ● → GPIO2 |
| WS2812 RGB | GPIO8 | Распаян на плате, провод не нужен |

**Не занимать:** GPIO12/13 (USB), GPIO16/17 (UART0), GPIO8/9/15 (strapping).

## 🖥️ Что на экране

Режим часов — секунды не показываются, освободившееся место отдано температуре:

```text
┌──────────────────────────────────────────────┐
│                        │                     │
│      27.3°             │      21:47          │
│ ────────────────────────────────────────────  │
│ SUN · 02 AUG 2026 · 1007hPa        [▮▮▮ ]87% │
└──────────────────────────────────────────────┘
```

Режим секундомера — крупный отсчёт во всю ширину, нижняя строка отдаёт дату под погоду:

```text
┌──────────────────────────────────────────────┐
│          01:23.456                           │
│ ────────────────────────────────────────────  │
│ II 27.3C · 1007hPa                 [▮▮▮ ]87% │
└──────────────────────────────────────────────┘
```

Детали раскладки:

- Температура ниже −9.9 °C теряет десятые (`-12°`), иначе строка упёрлась бы в разделитель; если и этого мало — шрифт автоматически уменьшается с 32 до 26 px.
- Маркер `II` слева появляется на паузе секундомера.
- Иконка батареи скрыта при питании от USB (`battery.valid == false`).
- Знак градуса рисуется кружком: в наборе `_tr` шрифтов U8g2 символа `°` нет.

## ⏱️ Секундомер: как держится синхронизация

Секундомер идёт на двух независимых часах: `millis()` на устройстве и `performance.now()` в браузере. Ведущим считается устройство, но наивная синхронизация по его показаниям даёт стабильное отставание, потому что телеметрия приходит с задержкой. Поэтому:

- браузер раз в 2 секунды шлёт `ping:<токен>`, получает `pong:<токен>:<state>:<elapsed>` и поправляет ответ на половину измеренного RTT;
- замеры с распухшим RTT отбрасываются, расхождение меньше 40 мс игнорируется, большое — выбирается плавно (35–40 % за замер), чтобы цифры не прыгали назад;
- на паузе счётчик заморожен, поэтому там берётся точное значение без поправки;
- пока идёт отсчёт, modem-sleep отключается: сон радио добавлял к доставке пакетов до 0.9 с.

Измеренный RTT в локальной сети — медиана **~9 мс**, разброс сдвига единицы миллисекунд. Текущий RTT виден в шапке карточки секундомера на дашборде.

**Плавность отрисовки.** Полный кадр OLED стоит ~24 мс (8 КБ буфера по SPI на 10 МГц), поэтому 25 раз в секунду его гнать нельзя. Между секундами меняется только поле `.mmm`, и его полоска отправляется отдельно через `updateDisplayArea()` — это ~2 мс. Полный кадр рисуется раз в секунду, когда меняется `MM:SS`. Итого 25 fps при загрузке ядра около 8 %.

## 🚀 Сборка и прошивка

Официальная платформа `espressif32` **не поддерживает ESP32-C6** (застряла на Arduino core 2.x). Используется форк **pioarduino** — он уже прописан в `platformio.ini`.

```bash
# 1. В src/config.h укажи Wi-Fi (только 2.4 ГГц), TZ и, при необходимости, пины
# 2. Сборка и прошивка
pio run -t upload
pio device monitor      # затем нажми RST
```

Ожидаемый лог при старте:

```text
=== ESP32-C6 Clock + Weather boot ===
CPU @ 80 MHz
[BMP280] Инициализация успешна.
[Battery] АЦП на GPIO2, делитель 1:2.0
Connecting to <SSID>....
IP: 192.168.x.x
mDNS: http://clock.local
NTP sync. OK
HTTP :80  WS :81
[hb] up=5s wifi=OK ip=... rssi=-50 heap=297256 clients=0 chip=41.3C bmp=22.5C p=1013hPa bat=-1%
```

> Пока дисплей не подпаян — поставь `#define HAS_DISPLAY 0` в `config.h`, чтобы U8g2 не гонял вслепую кадр 8 КБ каждую секунду на несуществующую панель.

### Разделы и флеш

`platformio.ini` задаёт 4 МБ флеша и таблицу `huge_app.csv` — один app-раздел на 3 МБ вместо двух по 1.25 МБ. Так сделано потому, что OTA в проекте нет, а при схеме `default.csv` прошивка занимала ~95 % слота и почти не оставляла запаса.

Текущий расход: **флеш 39.9 %** (1.26 МБ из 3 МБ), **RAM 15.8 %** (52 КБ из 320 КБ).

Waveshare указывает для C6-Zero чип **ESP32-C6FH8 с 8 МБ флеша**, но ранние ревизии шли с 4 МБ. Проверить свою плату:

```bash
~/.platformio/penv/bin/esptool --port /dev/ttyACM0 flash-id
```

Смена таблицы разделов означает, что **первая прошивка после неё идёт только по USB**.

## 🔧 Грабли и решения

### Прошивка «залипает» на секунды, если монитор не открыт

Самая коварная из встреченных. `Serial` здесь — нативный USB-CDC (`ARDUINO_USB_CDC_ON_BOOT=1`), и его `write()` блокирующий: пока хост держит порт открытым, но никто не вычитывает данные, буфер переполняется и `Serial.printf()` встаёт колом, останавливая весь `loop()`.

Симптомы: секундомер на дисплее отстаёт от браузера на несколько секунд, отклик по сети скачет пачками. Замер одного и того же теста:

| | RTT медиана | сдвиг счётчика |
| --- | --- | --- |
| Монитор не открыт | **4106 мс** (пики 12.5 с) | −6137 мс |
| Монитор открыт | 9.3 мс | разброс 29 мс |

Лечится одной строкой в `setup()`:

```cpp
Serial.setTxTimeoutMs(0);   // лишний вывод теряется, но loop() не встаёт
```

### Serial-монитор пуст

USB-C на C6-Zero подключён к **нативному USB Serial/JTAG**, а не к отдельной UART-микросхеме. Без флагов `Serial` уходит в UART0 (GPIO16/17), который к разъёму не подведён. В `platformio.ini` уже есть:

```ini
build_flags =
    -DARDUINO_USB_MODE=1
    -DARDUINO_USB_CDC_ON_BOOT=1
```

Правка `platformio.ini` **не меняет чип** — нужна пересборка и повторная заливка:

```bash
pio run -t clean && pio run -t upload
```

### `OSError: [Errno 71] Protocol error` при заливке

esptool пытается дёрнуть линию **RTS** для автосброса в download-режим, а нативный USB-JTAG этого не умеет. Решения:

1. Вручную: зажать **BOOT** → коротко нажать **RST** → отпустить **BOOT** → `pio run -t upload`
2. Или отключить автосброс:
   ```ini
   upload_flags =
       --before=no_reset
       --after=hard_reset
   ```

### `Could not open /dev/ttyS0`

Автоопределение порта промахнулось: `ttyS0` — это COM материнской платы. Плата — `/dev/ttyACM0`.

```bash
pio device list                                   # посмотреть реальный порт
pio run -t upload --upload-port /dev/ttyACM0
```

Или прописать в `platformio.ini`: `upload_port = /dev/ttyACM0`.
Порт занят или залип после неудачной заливки — **передёрни USB-кабель**, часто этого достаточно. Монитор при заливке должен быть закрыт: USB-CDC один на всё.

### `riscv32-esp-elf-g++: not found` (Error 127)

Проблема окружения, не кода:

- Тулчейн скачан частично → `rm -rf ~/.platformio/packages/toolchain-riscv32-esp* .pio && pio run`
- Сборка в **Alpine/musl** Docker → prebuilt-тулчейн собран под glibc и не запускается. Нужен Debian/Ubuntu-образ (например, `python:3.12-slim`).

## 🌡️ Температура и нагрев

Результаты измерений на реальной плате (комнатная ~23 °C):

| Режим | Показание |
| --- | --- |
| Wi-Fi выключен, 80 МГц | **53–55 °C** ← артефакт датчика, см. ниже |
| Wi-Fi подключён, простой | **36–37 °C** |
| Полная прошивка, открыт дашборд | **40–43 °C** |
| 160 МГц в простое | **+0 °C** (простаивающее ядро клок-гейтится) |

> **Встроенный датчик врёт при неинициализированном радио.** Сенсор делит аналоговые цепи с RF-подсистемой: с выключенным Wi-Fi он показывает ~55 °C при реальных ~36 °C. После старта Wi-Fi показания «падают» на 12–15 градусов за пару минут — это не остывание, а приход датчика в норму. Верить показаниям можно только при активном Wi-Fi; за абсолютной точностью — к BMP280.

Что снижает нагрев:

- `setCpuFrequencyMhz(80)` вместо 160 (под нагрузкой заметно, в простое — нет)
- `WiFi.setSleep(true)` + `esp_wifi_set_ps(WIFI_PS_MAX_MODEM)` — радио спит между маячками. На время работы секундомера сон выключается ради точности отсчёта и включается обратно при сбросе
- `HAS_DISPLAY 0`, пока панель не подпаяна
- broadcast по WebSocket не отправляется, если нет ни одного клиента
- Питание от 3.3 В (или от банки 4.2 В) вместо 5 В USB: на LDO AMS1117 падает меньше напряжения → меньше тепла рядом с чипом

40–43 °C на кристалле — **штатный режим**, а не перегрев: предел чипа 105 °C.

### Почему нет метрики «CPU load»

Мгновенную загрузку CPU на этой платформе честно измерить нельзя: при включённом энергосбережении ядро останавливается в light-sleep, и любой счётчик простоя принимает сон за нагрузку — метрика показывала 95–99 % на фактически простаивающем устройстве. Вместо неё на дашборде выводится **число подключённых клиентов** — точное и полезное.

## 🌐 API

| Метод | Путь | Описание |
| --- | --- | --- |
| GET | `/` | Дашборд |
| GET | `/api/stats` | Полное состояние: часы, погода, батарея, сеть |
| GET | `/api/time` | Время, дата, uptime, timestamp |
| GET | `/api/weather` | Метео + батарея (temp, pressure, QNH, altitude, trend, forecast) |
| POST | `/api/brightness` | `value=0..100` (ручная) или `auto=1` |
| POST | `/api/power` | `on=1` / `on=0` |
| POST | `/api/reboot` | Перезагрузка |

```bash
curl http://clock.local/api/stats
curl -X POST http://clock.local/api/brightness -d "value=80"
curl -X POST http://clock.local/api/power -d "on=0"
```

### WebSocket `ws://<IP>:81`

Раз в секунду прилетает полное состояние в JSON (то же, что `/api/stats`). Команды текстом:

| Команда | Ответ | Назначение |
| --- | --- | --- |
| `sw:start` | рассылка состояния | Запуск секундомера |
| `sw:pause` | рассылка состояния | Пауза |
| `sw:reset` | рассылка состояния | Сброс |
| `ping:<токен>` | `pong:<токен>:<state>:<elapsed>` | Замер задержки для синхронизации |

`ping` обрабатывается по «горячему» пути — без логов и без рассылки JSON, чтобы не искажать замер.

## 🏠 Home Assistant и Apple Home

MQTT выключен по умолчанию — при `MQTT_ENABLED false` его код вообще не компилируется. Включение в `config.h`:

```cpp
#define MQTT_ENABLED  true
#define MQTT_SERVER   "192.168.1.X"
```

После прошивки устройство само публикует HA Discovery — в Home Assistant появляются температура, давление, высота и батарея без ручной настройки (топики `clock/weather/*`).

**Дальше в Apple Home:** `Настройки → Устройства и службы → Добавить интеграцию → HomeKit Bridge`, выбрать нужные сущности, отсканировать QR-код приложением «Дом».

> Zigbee в Apple Home не поддерживается в принципе. Нативный Matter over Thread на C6 требует переезда на ESP-IDF + esp-matter (в Arduino-ядре Matter собран только под Wi-Fi, а OpenThread на C6 падает на инициализации). Мост через Home Assistant — самый простой рабочий путь.
> Давление в Apple Home не отобразится: HomeKit не имеет типа «барометр». Температура и батарея — отображаются.
