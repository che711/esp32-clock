# ESP32-C6 Clock + Weather ⏰🌡️

Настольные Wi-Fi-часы с большим OLED SSD1322 256×64 **и** метеостанцией на BMP280.
Одна плата **Waveshare ESP32-C6-Zero**, живой веб-дашборд, REST API, WebSocket, MQTT/Home Assistant.

Объединение двух проектов: `esp32-clock` + `esp32_zigbee_temperature`.

---

## ✨ Возможности

**Часы**

- Крупное время `HH:MM` и температура на одном экране, разделённые вертикальной чертой
- Автоматический переход зима/лето по POSIX-`TZ`, ре-синхронизация NTP раз в 6 часов
- Авто-яркость по времени суток, живая ручная регулировка ползунком по перцептивной шкале, полное отключение экрана
- Секундомер `MM:SS.mmm`, после 60 минут → `HH:MM:SS`, круги (laps) в браузере
- Отсчёт на OLED и в браузере идёт синхронно с компенсацией сетевой задержки — см. раздел «Секундомер» ниже

**Метео**

- Температура, давление (гПа / мм рт. ст.), высота, QNH, плотность воздуха
- Тренд давления и простой прогноз (☀️ / ⛅ / 🌧️)
- Мониторинг батареи 18650 (делитель + кривая разряда Li-ion)
- Два уровня энергосбережения: эконом по умолчанию, обычный на время секундомера

**Сеть и интеграции**

- Веб-дашборд с live-обновлением по WebSocket, светлая/тёмная тема, сворачиваемые блоки
- REST API + WebSocket, доступ по `http://clock.local` (mDNS)
- MQTT + Home Assistant Discovery → отсюда же в **Apple Home** (см. ниже)
- WS2812 статус-индикация, авто-реконнект Wi-Fi

> OTA в проекте нет: она была убрана, и освободившийся второй app-слот отдан под один
> раздел на 3 МБ (см. [Разделы и флеш](#разделы-и-флеш)). Прошивка — по USB.

## 📌 Распиновка

Используются **только боковые гребёнки**. Пины `6, 7, 8, 9, 12, 13, 23` на них не выведены — они в нижнем торцевом ряду, для проводного монтажа неудобны.

```text
        ESP32-C6-Zero
   ЛЕВАЯ                ПРАВАЯ
   5V                   TX (16)
   GND  ← дисплей 1     RX (17)
   3V3  ← дисплей 2,12  14
   0                    15
   1                    18 → дисплей 4  (CLK)
   2    → батарея ADC   19 → дисплей 5  (DIN)
   3                    20 → дисплей 14 (DC)
   4    → BMP280 SDA    21 → дисплей 15 (RST)
   5    → BMP280 SCL    22 → дисплей 16 (CS)
```

OLED разведён на правый ряд одним шлейфом: SPI — самые быстрые линии в схеме, тянуть их с изнанки платы не стоит. Слева остаются BMP280 (4, 5) и батарея (2).

Свободный резерв: `0, 1, 3, 14, 15` на гребёнках. Все пины меняются в `src/config.h`.

### Дисплей SSD1322 (16 контактов)

На плате модуля контакты просто пронумерованы 1…16.

| Пин | Сигнал | Куда |
| --- | --- | --- |
| 1 | GND | **GND** |
| 2 | VCC | **3V3** |
| 3 | NC | **NC** |
| 4 | SCLK | **GPIO18** |
| 5 | SDIN | **GPIO19** |
| 6–11 | D2–D7 | **GND** |
| 12 | RD# | **3V3** (вместе с пином 2) |
| 13 | WR# | **GND** |
| 14 | D/C | **GPIO20** |
| 15 | RST | **GPIO21** |
| 16 | CS | **GPIO22** |

> **Почему 6–13 не бросают в воздух.** Это линии параллельной шины, в режиме 4-wire SPI они не используются, но даташит SSD1322 требует задавать неиспользуемым входам определённый уровень. `RD#` активен низким уровнем, поэтому его держат на плюсе (неактивное состояние), остальные — на земле.

### Перемычки режима интерфейса

На обороте модуля напечатана таблица `R5 R6 R7 R8` со строками `3SPI / 4SPI / 80XX / 68XX`.
Нужен режим **4SPI**: запаяны **R5 и R8**, позиции R6 и R7 — пустые (BS1=0, BS0=0).
Если модуль в параллельном режиме или 3SPI — экран просто останется тёмным без ошибок в логе.

### Прочее

| Узел | Пин | Примечание |
| --- | --- | --- |
| BMP280 SDA / SCL | GPIO4 / GPIO5 | Strapping-пины, но для I²C безопасно: подтяжки модуля тянут вверх, что совпадает с состоянием при загрузке |
| Батарея (делитель) | GPIO2 | ADC1_CH2. Схема и калибровка — в разделе [Питание и зарядка](#-питание-и-зарядка) |
| WS2812 RGB | GPIO8 | Распаян на плате, провод не нужен |

**Не занимать:** GPIO12/13 (USB), GPIO16/17 (UART0), GPIO8/9/15 (strapping).

## 🖥️ Что на экране

Режим часов — секунды не показываются, освободившееся место отдано температуре:

```text
┌──────────────────────────────────────────────┐
│                        │                     │
│      27.3°             │      21:47          │
│ ────────────────────────────────────────────  │
│ SUN · 02 AUG 2026 · 1007hPa        [▮▮▮ ]87% │
└──────────────────────────────────────────────┘
```

Режим секундомера — крупный отсчёт во всю ширину, нижняя строка отдаёт дату под погоду:

```text
┌──────────────────────────────────────────────┐
│          01:23.456                           │
│ ────────────────────────────────────────────  │
│ II 27.3C · 1007hPa                 [▮▮▮ ]87% │
└──────────────────────────────────────────────┘
```

Детали раскладки:

- Температура ниже −9.9 °C теряет десятые (`-12°`), иначе строка упёрлась бы в разделитель; если и этого мало — шрифт автоматически уменьшается с 32 до 26 px.
- Маркер `II` слева появляется на паузе секундомера.
- Иконка батареи скрыта при питании от USB (`battery.valid == false`).
- На 20 % заряда и ниже температура уступает место крупной перечёркнутой батарее: цифру в углу легко не заметить, знак во всё левое поле — нет. Перечёркивание выходит за габарит корпуса батареи: пока диагональ упиралась в рамку изнутри, она читалась как шкала заряда наискось, а не как запрет.
- Ниже 15 % крупный знак и иконка в строке статуса мигают синхронно, секунда на секунду. Проценты рядом с иконкой не мигают — числу движение только мешает читаться, да и место под него всё равно занято.
- Знак градуса рисуется кружком: в наборе `_tr` шрифтов U8g2 символа `°` нет.

## ⏱️ Секундомер: как держится синхронизация

Секундомер идёт на двух независимых часах: `millis()` на устройстве и `performance.now()` в браузере. Ведущим считается устройство, но наивная синхронизация по его показаниям даёт стабильное отставание, потому что телеметрия приходит с задержкой. Поэтому:

- браузер раз в 2 секунды шлёт `ping:<токен>`, получает `pong:<токен>:<state>:<elapsed>` и поправляет ответ на половину измеренного RTT;
- замеры с распухшим RTT отбрасываются, расхождение меньше 40 мс игнорируется, большое — выбирается плавно (35–40 % за замер), чтобы цифры не прыгали назад;
- на паузе счётчик заморожен, поэтому там берётся точное значение без поправки;
- пока идёт отсчёт, modem-sleep отключается: сон радио добавлял к доставке пакетов до 0.9 с.

Измеренный RTT в локальной сети — медиана **~9 мс**, разброс сдвига единицы миллисекунд. Текущий RTT виден в шапке карточки секундомера на дашборде.

**Плавность отрисовки.** Полный кадр OLED стоит ~24 мс (8 КБ буфера по SPI на 10 МГц), поэтому 25 раз в секунду его гнать нельзя. Между секундами меняется только поле `.mmm`, и его полоска отправляется отдельно через `updateDisplayArea()` — это ~2 мс. Полный кадр рисуется раз в секунду, когда меняется `MM:SS`. Итого 25 fps при загрузке ядра около 8 %. От часа формат становится `HH:MM:SS`, дробить там нечего — полный кадр уходит по-прежнему раз в секунду, на смену значения, а не на каждый вызов.

**Круги живут в браузере.** Устройство о них не знает: `sw:start` / `sw:pause` /
`sw:reset` — это всё, что оно принимает. Значит вкладке нужно самой понимать,
относятся ли записанные круги к тому замеру, что идёт на устройстве сейчас.
Одного состояния (`sw_state`) для этого мало: и после моргнувшей связи, и после
начатого заново замера оно одинаково говорит «идёт». Поэтому в снимке есть
`sw_gen` — номер замера, который меняется на сбросе и на старте из простоя, но
не на паузе и не на продолжении. Круги стираются только при смене номера или
при переходе устройства в простой; переподключение WebSocket посреди замера их
больше не уносит. Правило смены номера закреплено тестами `test_sw_gen_*`.

## 🚀 Сборка и прошивка

Официальная платформа `espressif32` **не поддерживает ESP32-C6** (застряла на Arduino core 2.x). Используется форк **pioarduino** — он уже прописан в `platformio.ini`.

```bash
# 1. В src/config.h укажи Wi-Fi (только 2.4 ГГц), TZ и, при необходимости, пины
# 2. Сборка и прошивка
pio run -t upload
pio device monitor      # затем нажми RST
```

Ожидаемый лог при старте:

```text
=== ESP32-C6 Clock + Weather boot ===
CPU @ 80 MHz
[BMP280] Инициализация успешна.
[Battery] АЦП на GPIO2, делитель 1:2.0
Connecting to <SSID>....
IP: 192.168.x.x
mDNS: http://clock.local
NTP sync. OK
Power mode -> normal (auto)
HTTP :80  WS :81
[hb] up=5s wifi=OK ip=... rssi=-50 heap=297256 clients=0 chip=41.3C bmp=22.5C p=1013hPa bat=-1% pm=normal
```

> Пока дисплей не подпаян — поставь `#define HAS_DISPLAY 0` в `config.h`, чтобы U8g2 не гонял вслепую кадр 8 КБ каждую секунду на несуществующую панель.

### Разделы и флеш

`platformio.ini` задаёт 4 МБ флеша и таблицу `huge_app.csv` — один app-раздел на 3 МБ вместо двух по 1.25 МБ. Так сделано потому, что OTA в проекте нет, а при схеме `default.csv` прошивка занимала ~95 % слота и почти не оставляла запаса.

Текущий расход: **флеш 39.9 %** (1.26 МБ из 3 МБ), **RAM 15.8 %** (52 КБ из 320 КБ).

Waveshare указывает для C6-Zero чип **ESP32-C6FH8 с 8 МБ флеша**, но ранние ревизии шли с 4 МБ. Проверить свою плату:

```bash
~/.platformio/penv/bin/esptool --port /dev/ttyACM0 flash-id
```

Смена таблицы разделов означает, что **первая прошивка после неё идёт только по USB**.

## 🔧 Грабли и решения

### Прошивка «залипает» на секунды, если монитор не открыт

Самая коварная из встреченных. `Serial` здесь — нативный USB-CDC (`ARDUINO_USB_CDC_ON_BOOT=1`), и его `write()` блокирующий: пока хост держит порт открытым, но никто не вычитывает данные, буфер переполняется и `Serial.printf()` встаёт колом, останавливая весь `loop()`.

Симптомы: секундомер на дисплее отстаёт от браузера на несколько секунд, отклик по сети скачет пачками. Замер одного и того же теста:

| | RTT медиана | сдвиг счётчика |
| --- | --- | --- |
| Монитор не открыт | **4106 мс** (пики 12.5 с) | −6137 мс |
| Монитор открыт | 9.3 мс | разброс 29 мс |

Лечится одной строкой в `setup()`:

```cpp
Serial.setTxTimeoutMs(0);   // лишний вывод теряется, но loop() не встаёт
```

### Подключение к Wi-Fi не должно жить в `loop()` циклом с `delay()`

Тот же класс проблемы, но своими руками. Подключение было написано как
`while (WiFi.status() != WL_CONNECTED && tries < 30) delay(500)` — на старте
это безобидно, а вот из `loop()` та же функция вызывается на реконнекте, и там
пятнадцать секунд встаёт всё: часы, секундомер, веб-сервер и опрос датчика.

Теперь это автомат: `wifiBeginConnect()` начинает ассоциацию,
`wifiConnectStep()` двигает её на шаг из `maintainNetwork()` и говорит, когда
закончилось. В `setup()` он же прокачивается на месте — там ждать можно, на
экране заставка, а `syncNTP()` следом без сети всё равно бессмысленна.

Вся работа «после связи» — `localIP`, режим радио, mDNS — собрана в
`wifiOnConnected()`. Это важнее, чем кажется: связь возвращается не только
через автомат, но и сама, авто-реконнектом стека. Раньше после такого возврата
`MDNS.begin()` не вызывался вовсе, и `clock.local` молчал до перезагрузки —
адрес по IP при этом работал, отчего симптом выглядел как проблема сети, а не
прошивки. Признак `wifiReady` отмечает, отработала ли эта функция для текущей
ассоциации; проверка связи раз в 10 с доводит до конца то, что поднялось мимо.

### Serial-монитор пуст

USB-C на C6-Zero подключён к **нативному USB Serial/JTAG**, а не к отдельной UART-микросхеме. Без флагов `Serial` уходит в UART0 (GPIO16/17), который к разъёму не подведён. В `platformio.ini` уже есть:

```ini
build_flags =
    -DARDUINO_USB_MODE=1
    -DARDUINO_USB_CDC_ON_BOOT=1
```

Правка `platformio.ini` **не меняет чип** — нужна пересборка и повторная заливка:

```bash
pio run -t clean && pio run -t upload
```

### `OSError: [Errno 71] Protocol error` при заливке

esptool пытается дёрнуть линию **RTS** для автосброса в download-режим, а нативный USB-JTAG этого не умеет. Решения:

1. Вручную: зажать **BOOT** → коротко нажать **RST** → отпустить **BOOT** → `pio run -t upload`
2. Или отключить автосброс:
   ```ini
   upload_flags =
       --before=no_reset
       --after=hard_reset
   ```

### `Could not open /dev/ttyS0`

Автоопределение порта промахнулось: `ttyS0` — это COM материнской платы. Плата — `/dev/ttyACM0`.

```bash
pio device list                                   # посмотреть реальный порт
pio run -t upload --upload-port /dev/ttyACM0
```

Или прописать в `platformio.ini`: `upload_port = /dev/ttyACM0`.
Порт занят или залип после неудачной заливки — **передёрни USB-кабель**, часто этого достаточно. Монитор при заливке должен быть закрыт: USB-CDC один на всё.

### `riscv32-esp-elf-g++: not found` (Error 127)

Проблема окружения, не кода:

- Тулчейн скачан частично → `rm -rf ~/.platformio/packages/toolchain-riscv32-esp* .pio && pio run`
- Сборка в **Alpine/musl** Docker → prebuilt-тулчейн собран под glibc и не запускается. Нужен Debian/Ubuntu-образ (например, `python:3.12-slim`).

## 🌡️ Температура и нагрев

Результаты измерений на реальной плате (комнатная ~23 °C):

| Режим | Показание |
| --- | --- |
| Wi-Fi выключен, 80 МГц | **53–55 °C** ← артефакт датчика, см. ниже |
| Wi-Fi подключён, простой | **36–37 °C** |
| Полная прошивка, открыт дашборд | **40–43 °C** |
| 160 МГц в простое | **+0 °C** (простаивающее ядро клок-гейтится) |

> **Встроенный датчик врёт при неинициализированном радио.** Сенсор делит аналоговые цепи с RF-подсистемой: с выключенным Wi-Fi он показывает ~55 °C при реальных ~36 °C. После старта Wi-Fi показания «падают» на 12–15 градусов за пару минут — это не остывание, а приход датчика в норму. Верить показаниям можно только при активном Wi-Fi; за абсолютной точностью — к BMP280.

Что снижает нагрев:

- `setCpuFrequencyMhz(80)` вместо 160 (под нагрузкой заметно, в простое — нет)
- `WiFi.setSleep(true)` + `esp_wifi_set_ps(WIFI_PS_MAX_MODEM)` — радио спит между маячками. На время работы секундомера сон выключается ради точности отсчёта и включается обратно при сбросе
- `HAS_DISPLAY 0`, пока панель не подпаяна
- broadcast по WebSocket не отправляется, если нет ни одного клиента
- Питание от 3.3 В (или от банки 4.2 В) вместо 5 В USB: на LDO падает меньше напряжения → меньше тепла рядом с чипом

40–43 °C на кристалле — **штатный режим**, а не перегрев: предел чипа 105 °C.

### Почему нет метрики «CPU load»

Мгновенную загрузку CPU на этой платформе честно измерить нельзя: при включённом энергосбережении ядро останавливается в light-sleep, и любой счётчик простоя принимает сон за нагрузку — метрика показывала 95–99 % на фактически простаивающем устройстве. Вместо неё на дашборде выводится **число подключённых клиентов** — точное и полезное.

## 🌐 API

| Метод | Путь | Описание |
| --- | --- | --- |
| GET | `/` | Дашборд |
| GET | `/api/stats` | Полное состояние: часы, погода, батарея, сеть |
| GET | `/api/time` | Время, дата, uptime, timestamp |
| GET | `/api/weather` | Метео + батарея (temp, pressure, QNH, altitude, trend, forecast) |
| POST | `/api/brightness` | `value=0..100` (ручная, `0` гасит панель) или `auto=1` |
| WS | `br:<0..100>` / `br:auto` | то же, но по сокету — живая подстройка ползунком |
| POST | `/api/power` | `on=1` / `on=0` (ночью `on=1` — на 30 с; при заряде ≤ 5 % — отказ) |
| POST | `/api/powermode` | `mode=normal\|eco` |
| POST | `/api/reboot` | Перезагрузка |

Булевы параметры (`on`, `auto`) признают истиной только `1`, `true`, `on`, `yes`
— регистр не важен. Всё прочее, включая пустое значение, читается как ложь.
Раньше проверка была «всё, кроме строки `0`», и `on=false` включало экран.

`brightness_pct` в `/api/stats` — доля перцептивной шкалы, то есть положение
ползунка, а не доля тока панели (см. [Шкала яркости](#-шкала-яркости)).
Пересчёт в обе стороны замкнут: записанное значение читается обратно тем же.

```bash
curl --compressed http://clock.local/
curl http://clock.local/api/stats
curl -X POST http://clock.local/api/brightness -d "value=80"
curl -X POST http://clock.local/api/power -d "on=0"
curl -X POST http://clock.local/api/powermode -d "mode=eco"
```

Дашборд отдаётся предсжатым (`Content-Encoding: gzip`), поэтому для `curl`
нужен `--compressed`. Ответы `/api/*` не сжимаются.

### Проверка `Origin` у изменяющих запросов

Три `POST`-ручки и рукопожатие WebSocket сверяют заголовок `Origin`. Причина:
любая открытая в браузере страница может отправить на устройство `POST` или
открыть к нему WebSocket — код при этом выполняется в браузере, который уже
находится в вашей локальной сети, так что сама сеть границей не является.
Прочитать ответ чужая страница не сможет (запретит CORS), но перезагрузка
или сброс секундомера к этому моменту уже произойдут.

`Origin` проставляет сам браузер, и подделать его со страницы нельзя:

- свой дашборд (`http://clock.local`, `http://<IP>`, с портом `:80` или без) — пропускается;
- чужой домен, `https://`, `null` из песочницы — `403 {"error":"foreign origin"}`,
  для WebSocket отказ в рукопожатии;
- **запрос без `Origin` пропускается** — его шлют `curl`, Home Assistant и любые
  скрипты. Защита рассчитана на чужую вкладку, а не на осознанный запрос,
  поэтому примеры выше и интеграции продолжают работать без изменений.

Логика сравнения — в `src/origin_check.h`, покрыта тестами (в том числе на
`http://clock.local.evil.com`, который прошёл бы при сравнении по префиксу).

### WebSocket `ws://<IP>:81`

Раз в секунду прилетает полное состояние в JSON (то же, что `/api/stats`). Команды текстом:

| Команда | Ответ | Назначение |
| --- | --- | --- |
| `sw:start` | рассылка состояния | Запуск секундомера |
| `sw:pause` | рассылка состояния | Пауза |
| `sw:reset` | рассылка состояния | Сброс |
| `br:<0..100>` | — | Яркость вживую: ползунок шлёт на каждом шаге жеста |
| `br:auto` | — | Вернуть авто-яркость по расписанию |
| `ping:<токен>` | `pong:<токен>:<state>:<elapsed>` | Замер задержки для синхронизации |

`ping` и `br:` обрабатываются по «горячему» пути — без логов и без рассылки
JSON. У `ping` это чтобы не исказить замер, у `br:` — чтобы десяток сообщений
в секунду не превращался в десяток килобайт рассылки и десяток строк в Serial.
Отправитель значение и так знает, остальные вкладки увидят его ближайшим
снимком.

## 🔋 Питание и зарядка

USB-C на плате нужен для прошивки и питания от сети. Автономно устройство
живёт от 18650 через модуль **TP4056 с защитой** — у него четыре площадки
`B+ B- OUT+ OUT-` и рядом с клеммами два дополнительных корпуса (DW01A +
8205A). Версия без защиты, где площадок только две, для литиевой банки не
годится.

```text
USB-C платы ──┬─────────────────────────────────→ 5V ESP32-C6-Zero
              │                                     ↑
              └─→ IN+  TP4056  OUT+ ───▶|───────────┘  SS34, катодом к плате
                  IN-          OUT-  ──────────────→ GND
                   │            │
                  GND       B+ / B- → 18650
```

**Диод обязателен.** На C6-Zero пин `5V` соединён с VBUS напрямую: без диода
эти 5 В при подключённом USB ушли бы обратно в `OUT+`, прошли насквозь через
полевики защиты и попали на банку мимо зарядного чипа. Шоттки (падение ~0.3 В
против 0.7 В у обычного кремниевого) этот путь запирает, а заодно даёт
бесплатный load sharing: при живом USB нагрузка висит на нём, а не на банке,
и TP4056 корректно видит момент окончания заряда.

Ток заряда задан резистором `Rprog`: штатные `122` (1.2 кОм) дают 1 А, что для
банки 2500–3000 мАч нормально, но модуль при этом ощутимо греется. Помягче —
`202` (2 кОм, ~580 мА).

**Про запас по напряжению.** Между банкой и чипом стоят две потери: 0.3 В на
диоде и dropout штатного LDO платы (маленькая микросхема в корпусе SOT-23
рядом с процессором, выноска ③ на схеме Waveshare — не AMS1117, тот в SOT-223
и на плату такого размера не поместился бы). У экономичных LDO этого класса
dropout 0.2–0.3 В, и работает всё примерно до 3.55 В на банке — то есть
доступна почти вся ёмкость.

Точную маркировку стоит прочитать на живой плате: если там окажется что-то
с большим dropout, нижняя граница поднимется до ~3.8 В и половина ёмкости
станет недоступной. Обходится это только заменой LDO на импульсный
преобразователь прямо на пин `3V3`.

### Делитель напряжения

`OUT+ ──[100к]──●──[100к]── GND`, точка `●` → `GPIO2`, и **обязательно** 100 нФ
с этой точки на землю.

| Элемент | Зачем именно так |
| --- | --- |
| 1:2 | 4.2 В / 2 = 2.1 В, линейный участок АЦП при 11 dB тянется до ~2.45 В |
| 100к + 100к | 21 мкА утечки; меньше — сажает банку, больше — АЦП начинает врать |
| допуск 1 % | пятипроцентные дают до 5 % ошибки отношения |
| 100 нФ | АЦП при выборке кидает в источник импульс заряда, 50 кОм его не отдают |

Верхний резистор цепляется к `OUT+`, а не к клемме банки: при срабатывании
защиты по переразряду делитель отключается вместе с нагрузкой и не досасывает
мёртвый аккумулятор.

Калибровка: замерить мультиметром напряжение на банке, поделить на показание
в дашборде, результат записать в `BATTERY_CAL`. Коэффициент линейный, поэтому
калиброваться лучше в середине разряда (3.7–3.8 В), где кривая самая крутая.
Расхождение в пределах 1 % — это паспортная точность АЦП, ловить его смысла нет.

**Границы правдоподобия и полный заряд.** Замер вне `2.80…4.60 В`
(`battery_calc.h`) считается признаком того, что банки нет: `valid` сбрасывается,
а вместе с ним пропадают и иконка на экране, и плитка в дашборде — оба
индикатора висят на одном флаге. Верхняя граница держится с запасом над 4.2 В
намеренно: TP4056 в фазе стабилизации даёт на банке 4.2 В ±1 %, а линейный
`BATTERY_CAL`, снятый в середине разряда, добавляет к верхнему концу свои
2–3 % — и полностью заряженная банка показывает 4.31–4.33 В. С прежним
потолком 4.35 В индикатор пропадал ровно при полном заряде. Ошибиться в другую
сторону нечем: питание мимо банки даёт после пересчёта около 5 В и отсекается
всё равно.

Отброшенный замер печатается в Serial раз в 10 секунд —
`[Battery] 4.37 В вне 2.80..4.60 — считаем, что АКБ нет`. Без этой строки
пропавший индикатор выглядит загадкой: в heartbeat видно только `bat=-1%`.

**Плитка заряда в дашборде не прячется никогда.** Раньше при `bat_valid == false`
она получала `display: none` — сетка перекраивалась, и это читалось как поломка
дашборда, а не как «питание от USB». Теперь на её месте остаётся прочерк вместо
процентов, подпись `no battery` и последний пересчитанный замер (поле
`bat_raw_v`, отдаётся и при `valid == false`) — по нему сразу видно, банку сняли
или делитель показывает несуразицу.

**Просадка под нагрузкой.** Отключил USB — показание падает: через банку
потёк ток, и напряжение просело на внутреннем сопротивлении, пружинах
холдера и полевиках защиты. Это не ошибка измерения. Локализуется замером
милливольт на каждом участке под нагрузкой:

| Участок | Норма |
| --- | --- |
| плюс банки → `B+` | до 10 мВ |
| минус банки → `B-` | до 10 мВ |
| `B-` → `OUT-` (полевики защиты) | 10–20 мВ |
| `OUT-` → `GND` платы | до 10 мВ |

Больше нормы — виноват обычно держатель: пружины дешёвых холдеров дают
0.1–0.5 Ом. Радикально лечится пайкой проводов к банке напрямую.

### Фильтр замеров

Отсчёты АЦП набираются **по одному за итерацию `loop()`** с шагом 25 мс: пачка
из 16 подряд укладывается в миллисекунду и может целиком попасть в импульс
передачи Wi-Fi, когда потребление скачет с 80 до 300 мА. Растянутый на 0.4 с
набор захватывает и провалы, и паузы, а **медиана** выбрасывает провалы вместо
того, чтобы размазывать их по результату, как это делает среднее.

Между наборами — экспоненциальное сглаживание (`BATTERY_SMOOTH`). Скачок больше
`BATTERY_JUMP_V` фильтр распознаёт как событие (сняли USB, поменяли банку) и
перезапускается, а не ползёт к новому уровню полминуты.

Без фильтра цифра заметно дёргалась: в средней части кривой разряда крутизна
доходит до **2 мВ на процент** (участок 3.79 → 3.77 В), а 10 мВ — это обычный
шум АЦП.

## 🌙 Энергосбережение

### Когда какой уровень

| Условие | Уровень |
| --- | --- |
| Секундомер начат (идёт или на паузе) | **обычный** |
| Всё остальное | **эконом** |

Эконом — базовое состояние, а не аварийное. Полная мощность нужна ровно тогда,
когда с часами работают, то есть на время замера; в остальное время смотреть на
экран и держать радио наготове круглые сутки незачем.

Уровень выбирает пользователь, а поправляет его ровно одно обстоятельство —
секундомер. **Заряд уровень не выбирает.** Он трогает три рубежа: на
`BATTERY_CRITICAL_PCT` (20 %) вместо погоды встаёт перечёркнутая батарея,
на `BATTERY_BLINK_PCT` (15 %) она начинает мигать, на `POWER_SCREEN_OFF_PCT`
(5 %) панель гаснет совсем.

<details>
<summary>Третьим был «выживание». Почему его убрали</summary>

Он выключал Wi-Fi ниже порога заряда и экономил около суток работы. Но эти
сутки часы были глухими: ни дашборда, ни секундомера, ни свежего времени, —
и связь пропадала ровно тогда, когда на заряд и хотелось посмотреть.

Хуже того, выключенное радио уносило единственный канал управления, и подсистема
питания почти целиком состояла из подпорок под это одно свойство:

- `POWER_MANUAL_SURVIVAL_MS` — срок ручной фиксации, потому что иначе из режима
  нечем выйти;
- `maintainSurvivalRadio()`, `radioOff()`, окно NTP раз в сутки со своими
  `ntpWaking` / `ntpRequested` / `ntpWakeStart` — полсотни строк, чтобы часы
  не уезжали;
- вето по заряду над выбором пользователя, `PowerHold`, расхождение
  «выбрано / работает», поле `power_hold` и его объяснения в дашборде — потому
  что зафиксированное руками выживание не отпускало даже полную банку;
- отдельный тумблер «By charge» в дашборде, чтобы развести «решает заряд» и
  «решаю я».

Ничего из этого не нужно, когда режимов два и оба держат радио живым. А работу,
ради которой он был нужен, делают два рубежа: гашение панели на 5 % снимает
около сотни миллиампер из ста семидесяти (замеры — ниже, «Что сколько ест»)
и заодно убирает просадку; предупреждение на 20 % говорит, что пора заряжать.

Что потеряли честно: импульсы передачи Wi-Fi (до 300 мА) у самого дна больше
никто не глушит. По прикидке просадка на них ~35 мВ и рубеж 3.55 В не пробивает,
но это расчёт, а не замер. Если brownout всё же появится, лечится рубежом
«радио прочь» по образцу экранного — без режима, срока и фиксаций.

</details>

**Время суток режим не меняет.** Ночь — это только про экран: в экономе панель
гасится с 22:00 до 06:00, а Wi-Fi остаётся поднятым. Гасить ночью ещё и радио
значило бы, что устройства нет ни в сети, ни под рукой — секундомер не запустить,
дашборд не открыть, — ради выигрыша в единицы миллиампер.

### Лестница по заряду

| Заряд | Напряжение | Что происходит |
| --- | --- | --- |
| ≤ 20 % | ~3.76 В | **перечёркнутая батарея вместо температуры** в левой половине циферблата, жёлтый мигок LED, запись в журнал |
| ≤ 15 % | ~3.75 В | **знак и иконка мигают** секунда на секунду |
| ≤ 5 % | 3.70 В | **экран гаснет совсем**, независимо от уровня и времени суток; кнопка включения получает отказ |
| 0 % | 3.65 В | **часы уходят в deep sleep** и перестают тянуть из банки |

Три ступени, и все — рубежи, а не режимы: первая говорит «пора заряжать» так,
чтобы было видно с другого конца комнаты, вторая настаивает движением, когда
к статичному знаку уже пригляделись, третья снимает с банки крупнейшего
потребителя. Ещё одной была смена режима на «выживание» — убрана вместе с самим
режимом (почему — выше, в разделе про уровни).

Мигание — отдельный порог, а не тот же самый, потому что говорит другое.
Знак на 20 % — это «зарядить бы сегодня»; на 15 % банке остаётся пологий хвост
до гашения панели, и там уже «зарядить сейчас». Статичный символ за пару часов
примелькается и перестанет читаться как тревога, а движение в поле зрения
замечают, даже не глядя на часы прямо. Такт держится не отдельным таймером:
полный кадр и так перерисовывается ровно на смене секунды, поэтому фаза —
это парность самой секунды (`battWarnVisible()` в `display_calc.h`). Два
независимых периода рано или поздно разъезжаются, и знак застревал бы
зажжённым на два кадра подряд; заодно внеочередная перерисовка из дашборда
внутри той же секунды повторяет ту же фазу, а не даёт лишний моргок.

**Ноль шкалы — 3.65 В**, и это выбор в пользу ресурса банки, а не пробега.

Технически устройство живёт ниже: между аккумулятором и чипом стоят диод и
LDO, и работает всё примерно до 3.55 В. Ноль когда-то там и стоял (3.50 В) —
«выжимаем всё, что физически доступно». Но глубокий разряд Li-ion стоит циклов:
у элемента, который регулярно опускают к 3.5 В, ресурс в разы короче, чем
у того, что разворачивают на 3.65. Часы стоят на столе и заряжаются когда
удобно, так что пара лишних часов работы того не стоит.

Главный эффект тут не в самой цифре, а в том, что **пороги заданы в процентах
и переезжают вместе с нулём**: гашение экрана (5 %) с этой кривой приходится
ровно на 3.70 В вместо прежних 3.60. Панель со всей её обвязкой — это ~100 мА
из 170 на полной яркости, и снимается она с банки на сотню милливольт раньше.

**Ноль шкалы — команда «стоп».** На нём часы уходят в `deep sleep` и
перестают тянуть из элемента вовсе: **~20 мкА** по даташиту (сам сон не
измерен) против измеренных **60–80 мА** с погашенным экраном. Без этого поднятый ноль защищал бы банку лишь наполовину — разряд
продолжался бы до brownout на 3.55 В, просто медленнее.

Будильник — таймер, потому что физической кнопки нет, а подключение USB чип
не перезагружает: питание идёт через тот же диод, и для спящего процессора
ничего не меняется. Поэтому раз в `POWER_SLEEP_CHECK_MS` (5 мин) часы
просыпаются, читают АЦП и решают — вставать или спать дальше. Проверка стоит
доли секунды: ни экран, ни радио на этом пути не поднимаются, до полного
`setup()` дело не доходит.

| Константа | Что задаёт |
| --- | --- |
| `POWER_SLEEP_PCT` = 0 | заряд, на котором засыпаем — дно шкалы, 3.65 В |
| `POWER_WAKE_PCT` = 10 | заряд, на котором встаём совсем — 3.72 В |
| `POWER_SLEEP_CONFIRM_MS` = 30 с | сколько ноль должен продержаться до сна |
| `POWER_SLEEP_CHECK_MS` = 5 мин | как часто просыпаться на проверку |

**Запас между порогами обязателен.** Во сне нагрузки нет, банка отдыхает
и напряжение само подрастает на десятки милливольт. Совпадай пороги — часы
вставали бы на этом отскоке, тут же садились обратно и грузились по кругу
каждые пять минут. 10 % это 3.72 В, выше любого отскока: туда доводит только
настоящая зарядка. Непересечение порогов закреплено тестом
`test_power_sleep_and_wake_do_not_overlap`.

**Ноль подтверждается 30 секундами.** Одиночный выброс АЦП не должен стоить
пяти минут темноты. Ноль на ровном месте маловероятен — медиана набора
и сглаживание его давят, — но цена ошибки тут велика.

**Время сон переживает.** RTC идёт и в глубоком сне, поэтому часы просыпаются
с верным временем и без похода в сеть: `setup()` проверяет, показывает ли
система правдоподобную дату, и если да — считает время синхронизированным.
Иначе экран рисовал бы прочерки при исправных часах, пока не дойдёт очередь
до NTP. Аптайм при этом обнуляется — сон это всё-таки перезагрузка.

**На USB часы не засыпают.** `battery.valid == false` означает, что процентов
нет, и усыплять не за что. То же правило работает и на пробуждении: если
банку вынули, часы встают, а не спят дальше.

Хвост кривой при этом **растянут, а не поджат** — и это не косметика. Раньше
между 3.74 В (20 %) и 3.72 В (10 %) умещалось десять процентов, то есть 2 мВ
на пункт — меньше собственного шума АЦП: индикатор прыгал на 5–10 % при
неподвижной банке. Теперь на те же десять процентов приходится 60 мВ, ниже —
ещё положе. Середину кривой растягивать нечем и незачем: на плато 3.77–3.79 В
у элемента действительно лежат целые десять процентов, это физика, а не шкала.

Рубежи заданы в процентах, но означают напряжение, поэтому переезжают вместе
с нулём шкалы: `BATTERY_CRITICAL_PCT` (20 %) приходится примерно на 3.76 В,
`BATTERY_BLINK_PCT` (15 %) — на 3.747 В, `POWER_SCREEN_OFF_PCT` (5 %) — ровно
на 3.70 В. Между предупреждением и гашением 60 мВ, и мигать знак начинает
примерно на середине этого промежутка — там же, где загорается «разряжена»
по `BATTERY_LOW_V` (3.74 В).

**Миллиампер-часы в дашборде — пересчёт, а не измерение.** Кулоновского
счётчика на плате нет, единственный датчик заряда — делитель на `GPIO2`,
поэтому `bat_mah` выводится из процентов через `BATTERY_USABLE_MAH`
(`config.h`, сейчас 3300 — паспортная ёмкость элемента). Знак `≈` в плитке
стоит именно поэтому.

Это верхняя граница: в шкалу помещается не вся банка, а только окно
4.20…3.65 В — ниже нуля шкалы заряд намеренно не выбирается. Сколько мА·ч
в это окно реально влезает, не измерено; выясняется одним прогоном до отсечки
с записью CSV, и тогда сюда встанет измеренное число.

Последний порог самый полезный. Панель — крупнейший потребитель, и её
отключение не только растягивает остаток, но и снимает просадку напряжения,
из-за которой устройство ушло бы в brownout раньше времени.

### Режимы

Два уровня. Выбираются из дашборда и через `POST /api/powermode`; сам по себе
поднимается только обычный, и только на время секундомера. Профили — в
`src/power_calc.h`, рубежи по заряду — в `config.h`.

**Выбранный уровень и рабочий.** Выбор живёт в `chosen`, рабочий — в `mode`,
и расходятся они ровно в одном случае: на время замера. Правило —
`powerEffectiveMode()` в `power_calc.h`, наружу расхождение идёт флагом
`power_pinned`, а дашборд по нему пишет `eco · running normal` и объяснение.
Без пометки это читалось бы как незалипшая кнопка, а не как «вернём со сбросом».

**Секундомер поднимает уровень до обычного — и поверх выбранного тоже.**
Замер запускают, чтобы на него смотреть, поэтому ни зафиксированный эконом, ни
ночной час экран погасить не могут: `swStart()` дёргает `powerLoop()` сразу,
уровень становится обычным (профиль `normal` ночного окна не знает), а
`screenSetPower(true)` добирает случай, когда панель выключили кнопкой в
дашборде.

**Но яркость при этом остаётся от выбранного уровня.** Это единственный
параметр, который берётся из `chosen`, а не из `mode` — и вынесен он оттуда
намеренно. Уровень поднимается ради расписания экрана, а полная яркость ехала
прицепом и стоила дороже всего остального вместе взятого:

| Час | Масштаб `normal` | Масштаб `eco` |
| --- | --- | --- |
| День (уровень 228) | 78.1 % тока панели | **25.0 %** |
| Вечер (181) | 46.9 % | **15.1 %** |
| Ночь (72) | 6.2 % | **2.0 %** |

Втрое на крупнейшем потребителе — при том, что читаемости полная яркость не
добавляет, эконом-уровень виден прекрасно. Связка закреплена тестом
`test_power_stopwatch_lifts_schedule_not_brightness`, чтобы её однажды не
«починили» обратно.

**Сон радио под замером ужимается, а не выключается.** `MAX_MODEM` холоднее
всех, но задерживает входящий пакет до ~0.9 с, и кнопки в браузере отвечают
с заметным опозданием. Поэтому на время замера ставится `MIN_MODEM` —
пробуждение на каждый маячок, вместе с `listen_interval = 1` из профиля
`normal` это около десятой секунды.

Раньше здесь стоял `WiFi.setSleep(false)`, то есть сон снимался совсем и
приёмник работал непрерывно — порядка 65 мА на ровном месте. Обосновано это
было «точностью отсчёта», но отсчёт идёт по `millis()` и от сна радио не
зависит вовсе: страдала только доставка команд, а её хватает и `MIN_MODEM`.

> **Секундомер теперь доступен всегда.** Раньше в выживании его было не
> запустить: Wi-Fi выключен, физической кнопки нет, а `sw:start` приходит
> только по сети. С уходом выживания радио живёт до конца разряда, и этой
> дыры больше нет.

| | Обычный | Эконом |
| --- | --- | --- |
| Когда включается сам | секундомер | стартовый уровень |
| Wi-Fi | всегда | всегда |
| Опрос BMP280 | 60 с | 2 мин |
| Яркость | 100 % | 60 % |
| Экран 22:00–06:00 | горит | гаснет |
| Мощность передатчика | 20 dBm | 11 dBm |
| `listen_interval` | 1 маячок | 5 маячков |
| Мигок WS2812 | есть | нет |

### Что сколько ест

Измерено лабораторным блоком питания вместо банки, при 4.2 В:

| Состояние | Ток |
| --- | --- |
| Экран выключен (`POST /api/power -d "on=0"`) | 60–80 мА |
| Экран включён, яркость 2 % — свечения практически нет | 100–120 мА |
| Экран на яркости около полной | 160–180 мА |

Отсюда раскладка на полной яркости — и она не та, из которой проект исходил
раньше:

| Статья | Ток | Доля |
| --- | --- | --- |
| Чип + Wi-Fi | 60–80 мА | ~41 % |
| Обвязка панели: DC-DC на VCC, контроллер, развёртка | ~40 мА | ~24 % |
| Свечение пикселей | до 60 мА | ~35 % |

Средняя строка видна именно на 2 %: по гамме 2.2 (`display_calc.h`) ползунок
на двух процентах — это 0.02 % тока панели, светиться там нечему, а сотня
миллиампер всё равно течёт. Значит, панель стоит денег уже самим фактом
включения, а не яркостью.

**Яркость — слабый рычаг.** От полной до нуля она даёт 35 % расхода, то есть
растягивает работу с 18 до 28 часов, не больше. Гашение панели убирает сразу
~100 мА, а дальше упирается в базовые 60–80 мА, которых проект пока не
касается вовсе: `esp_pm_configure()` и light sleep не включены, `loop()`
крутится на `delay()` при полной частоте, Wi-Fi ассоциирован и раз в секунду
рассылает снимок по WebSocket — даже когда дашборд никто не открыл. Это самая
крупная статья бюджета и единственная нетронутая.

При ~3100 мА·ч в окне 4.20–3.65 В (косвенная оценка, см. `BATTERY_USABLE_MAH`)
получается: полная яркость — ~18 ч, эконом днём — ~25 ч, экран выключен —
~44 ч, эконом с ночным гашением — **около 29 часов**.

Всё остальное — единицы миллиампер, включая сам делитель с его 21 мкА.
Импульсы передачи Wi-Fi (до 300 мА) в средний ток почти не входят, но дают
просадку напряжения, ради которой и стоит медианный фильтр в `battery.cpp`.

Прежние цифры в этом месте — «OLED 30–70 мА, Wi-Fi 20–30 мА, всё остальное
единицы миллиампер» — были прикидкой по даташитам, и обе основные ошиблись
в разы. Соседний абзац про рубеж 5 % при этом называл OLED «150–180 мА»,
и правы оказались обе цифры сразу: 150–180 берёт устройство целиком, а не
панель.

**Датчик и батарея опрашиваются врозь.** Температура и давление за минуту
никуда не убегают, поэтому BMP280 спрашивается редко. А вот заряд обновляется
каждую итерацию `loop()`: `batteryLoop()` всё равно считает его непрерывно,
копия структуры бесплатна, и от него зависят пороги гашения экрана — привязывать
их к периоду опроса погоды было бы неверно.

**Расписание экрана** — единственное, за что отвечает ночное окно
`POWER_NIGHT_ON_HOUR`/`POWER_NIGHT_OFF_HOUR`. В эконом-режимах подсветке
разрешено гореть ровно в «не ночь»; в обычном режиме расписание не действует
вовсе. Границы окна срабатывают всегда: в 22:00 панель гаснет, в 6:00
загорается снова — на прежних настройках яркости и независимо от того, чем она
была выключена накануне.

Раньше часы помнили не окно, а панель: флаг «погасили мы сами» взводился в
момент закрытия окна и только если панель в этот момент горела. Экран,
выключенный кнопкой днём, проходил 22:00 незамеченным — гасить было нечего, —
и в 6:00 включать было тоже нечего. Часы оставались тёмными до следующего
нажатия, и со стороны это выглядело случайностью: погасил вечером — утром
работают, погасил днём — нет. Теперь запоминается состояние окна, а экран
зажигается на переходе «нельзя → можно». Тем же переходом панель возвращается
после зарядки выше `POWER_SCREEN_OFF_PCT` и при переключении эконом → обычный:
в обоих случаях причина, по которой экран был погашен, исчезла, и ждать утра
незачем.

Ручное выключение при этом перестало быть вечным — оно живёт до ближайшего
открытия окна. Выключили в 10 утра — темно будет до 6 утра следующего дня.

**Ночью экран всё же включается по кнопке** — посмотреть на часы надо, а
физической кнопки на устройстве нет. Но не насовсем: команда зажигает панель
на `POWER_SCREEN_PEEK_MS` (30 с), после чего расписание гасит её само. Забыть
выключить экран легко, а цена забывчивости — крупнейший потребитель, горящий
до утра. Остаток отсчёта едет в дашборд полем `screen_peek` и виден прямо на
кнопке (`⏻ Display on · 27s`), иначе гашение через полминуты читалось бы как
сбой. Досрочное «выключить» снимает отсчёт сразу, наступившее утро — тоже.

**Порог заряда подсветкой не обходится.** Расписание она перебивает, рубеж
`POWER_SCREEN_OFF_PCT` — нет: ниже него `POST /api/power -d "on=1"` отвечает
отказом, а не зажигает панель на полминуты. Соблазн разрешить и здесь понятен —
узнать время на умирающей батарее ровно то, чего от часов в этот момент хотят, —
но 30 секунд OLED на исходе банки это не только миллиампер-часы: это просадка
напряжения, на которой чип уходит в brownout. Часы тогда не показывают время
напоследок, а выключаются совсем.

Отказ виден снаружи: `display_on` и в ответе, и в снимке — фактическое состояние
панели, а не то, что попросили, поэтому кнопка в дашборде честно остаётся в
положении «выключено».

**При питании от USB** рубежи по заряду не применяются: `battery.valid == false`
означает, что данных нет, и гадать по ним незачем. Перечёркнутая батарея не
появляется, экран по заряду не гаснет — но ночное расписание работает как
обычно: оно про то, смотрит ли кто-то на часы, а не про батарею.

## 🔆 Шкала яркости

Наивная реализация — `setContrast(pct * 255 / 100)` — на SSD1322 даёт шкалу,
у которой работают только два положения: ноль и «всё остальное». Причин две,
и обе пришлось лечить (`display_calc.h`).

**Регистров тока два, а не один.** Ток сегмента пропорционален произведению
`(contrast + 1) × (master + 1)`: Contrast Current (`0xC1`, 0..255) и Master
Current (`0xC7`, 0..15). Полный ход шкалы — 4096 ступеней, но `u8g2` ставит
master на максимум в инициализации и дальше трогает только `0xC1`. Вся
регулировка поэтому жила в верхних 6 % диапазона, а самый тусклый доступный
уровень — 1/256 полного тока — светит вполне заметно. Отсюда и провал между
«выключено» и «единица». Master-регистр шлём сами через `sendF("ca", 0xC7, …)`,
и нижняя ступень опускается до 1/4096.

**Восприятие нелинейно.** Ток линеен, глаз — нет: половина тока выглядит
примерно как три четверти яркости. На линейной шкале верхняя половина ползунка
почти не отличается на глаз, а вся заметная разница набита в нижние проценты.
Ток поэтому считается как степень 2.2 от положения ползунка — та же гамма, что
у sRGB, — и равные шаги ползунка дают примерно равные шаги на глаз.

| Ползунок | Ток от максимума | Было (линейно) |
| --- | --- | --- |
| 1 % | 0.02 % | 0.4 % |
| 10 % | 0.7 % | 10 % |
| 50 % | 22 % | 50 % |
| 100 % | 100 % | 100 % |

Регистры считает `panelDriveForLevel()`, покрытая тестами на монотонность и
границы.

**Таблица часов живёт на той же перцептивной шкале.** Уровни авто-яркости в
`brightnessForHour()` (`clock_utils.h`) — числа 0..255, и после перехода на
гамму они означают «столько-то яркости на глаз», а не долю тока. Прежние
`15/80/120/200` подбирались ещё под прямую запись в `0xC1`, то есть задавали
именно ток; прочитанные как перцептивные, они проваливали ночь с 6.3 % тока до
0.2 %, в тридцать раз, — на панели её было уже не разглядеть. Поэтому числа
пересчитаны обратно, `L = 255 · f^(1/2.2)`:

| Час | Уровень шкалы | Ток от максимума |
| --- | --- | --- |
| Ночь (22–06) | 72 | ≈ 6.3 % |
| Утро (06–08) | 151 | ≈ 31.6 % |
| День (08–20) | 228 | ≈ 78.5 % |
| Вечер (20–22) | 181 | ≈ 47.3 % |

Светимость авто-уровней тем самым та же, что была до гаммы, а перцептивной
шкалой пользуется ползунок — ради него всё и затевалось. Пересчёт закреплён
тестом `test_brightness_levels_keep_pre_gamma_output`, чтобы таблицу однажды
снова не прочитали как доли тока.

**Часы не встали — уровень всё равно выставляется.** Без синхронизации NTP час
неизвестен, применять расписание не к чему, и `applyAutoBrightness()` раньше
выходила первой же строкой: панель оставалась на стартовом уровне (максимум),
а заодно не срабатывал и порог `POWER_SCREEN_OFF_PCT` — устройство без сети
жгло экран на полную до самого brownout. Теперь без времени пропускается только
расписание: яркость берётся из `brightnessNoTime()` (вечерний уровень, метка
`No time` в дашборде), а рубеж по заряду считается как обычно — он от часа
не зависит.

**Ползунок регулирует вживую, а не по отпусканию.** Пока ручка едет, значение
уходит по уже открытому WebSocket командой `br:<0..100>`, с шагом не чаще
80 мс, — панель следует за пальцем. POST на каждый пиксель тут не годился:
HTTP-сервер на C6 однопоточный, и очередь коротких запросов он разгребает
медленнее, чем движется ручка. Итоговое значение всё равно закрепляется
обычным `POST /api/brightness` на `onchange`, так что потерянный по дороге
кадр ничего не решает. Путь `br:` намеренно обработан до логов и до рассылки
снимка: десяток строк в Serial и десяток килобайт JSON в секунду стоили бы
дороже самой регулировки. Origin у сокета проверяется на рукопожатии, так что
защита та же, что у POST.

**Трогать ползунок в авто-режиме можно.** Первое же движение по нему и есть
переход в ручной — кнопка `Manual` осталась, но искать её больше не нужно;
`Auto` рядом остаётся дорогой обратно. Раньше ручка в авто-режиме была
выключена (`pointer-events: none`), и «плавно подкрутить яркость» требовало
сперва догадаться нажать соседнюю кнопку.

**Ноль гасит панель.** Регистрами тока SSD1322 до конца не гасится: на нулевом
контрасте панель продолжает светить. Поэтому нулевая яркость уходит в
`setPowerSave(1)`, а `displayIsOn()` отдаёт фактическое состояние панели —
«экран сейчас виден?», а не «подано ли питание». Обратная команда `/api/power
-d "on=1"` при нулевой яркости получает **отказ**: в ответе `display_on: false`
и `refused: "brightness"`, а дашборд пишет в журнал, что надо поднять ползунок.

Раньше она вместо отказа молча подтягивала яркость до нижней читаемой ступени
(`CONTRAST_MIN_VISIBLE`, он же ночной уровень) — чтобы кнопка давала видимый
результат. Результат она давала, но ценой расхождения: ползунком в ручном
режиме владеет пользователь, со снимком он не сверяется, и дашборд продолжал
показывать 0 % при панели, светящей на 28 %. Ноль на ползунке поставлен руками
и значит «выключено»; отменять этот выбор без ведома владельца — не дело
прошивки, и честный отказ тут лучше видимого результата. Из того же решения
следует, что и старт секундомера при нулевой яркости панель не зажигает:
`swStart()` дёргает ту же команду и получает тот же отказ, отсчёт остаётся
в браузере.

Причин отказать включению теперь две, и `refused` их различает: `"battery"` —
заряд ниже `POWER_SCREEN_OFF_PCT`, лечится зарядкой; `"brightness"` — ползунок
в нуле, лечится ползунком. Советы противоположные, поэтому одного `display_on`
мало: пока дашборд видел только расхождение, он на любой отказ писал про
разряженную батарею — в том числе там, где батарея была ни при чём.

## 🧪 Тесты

Хелперы в `clock_utils.h` (форматирование времени, uptime, секундомера, пересчёт яркости, уровень RSSI) покрыты юнит-тестами, работающими на хосте без платы:

```bash
pio test -e native
```

## 📁 Структура

```text
platformio.ini            pioarduino (C6) + U8g2 + WebSockets + BMP280 + PubSubClient
src/
├─ config.h               ← все настройки и карта пинов
├─ main.cpp               жизненный цикл: WiFi, NTP, опрос датчиков, LED, loop()
├─ app.h                  общее состояние прошивки (владелец — main.cpp)
├─ display.h/.cpp         OLED: раскладка кадра, яркость, питание
├─ display_calc.h         уровень яркости → регистры тока SSD1322 (тесты)
├─ web_api.h/.cpp         HTTP :80 + WebSocket :81, сборка JSON
├─ stopwatch.h            автомат секундомера (покрыт тестами)
├─ clock_utils.h          хелперы форматирования (покрыты тестами)
├─ sensor.h/.cpp          BMP280: чтение датчика
├─ weather_calc.h         арифметика метео: тренд, прогноз, QNH (покрыто тестами)
├─ battery.h/.cpp         18650 через делитель напряжения
├─ battery_calc.h         кривая разряда и фильтр замеров (покрыто тестами)
├─ power.h/.cpp           режимы энергосбережения: радио, экран, периоды
├─ power_calc.h           профили и выбор режима по заряду (покрыто тестами)
└─ mqtt.h/.cpp            MQTT + Home Assistant Discovery
web/
└─ index.html             дашборд; при сборке жмётся в gzip и уходит во флеш
scripts/
└─ gen_web_ui.py          web/index.html → $BUILD_DIR/generated/web_ui_gz.h
```

Дашборд не тянет ничего из интернета: шрифты только системные, поэтому
страница одинаково открывается и в сети без выхода наружу.
