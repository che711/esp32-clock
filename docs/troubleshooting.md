## Прошивка «залипает» на секунды, если монитор не открыт

Самая коварная из встреченных. `Serial` здесь — нативный USB-CDC (`ARDUINO_USB_CDC_ON_BOOT=1`), и его `write()` блокирующий: пока хост держит порт открытым, но никто не вычитывает данные, буфер переполняется и `Serial.printf()` встаёт колом, останавливая весь `loop()`.

Симптомы: секундомер на дисплее отстаёт от браузера на несколько секунд, отклик по сети скачет пачками. Замер одного и того же теста:

| | RTT медиана | сдвиг счётчика |
| --- | --- | --- |
| Монитор не открыт | **4106 мс** (пики 12.5 с) | −6137 мс |
| Монитор открыт | 9.3 мс | разброс 29 мс |

Лечится одной строкой в `setup()`:

```cpp
Serial.setTxTimeoutMs(0);   // лишний вывод теряется, но loop() не встаёт
```

## Подключение к Wi-Fi не должно жить в `loop()` циклом с `delay()`

Тот же класс проблемы, но своими руками. Подключение было написано как
`while (WiFi.status() != WL_CONNECTED && tries < 30) delay(500)` — на старте
это безобидно, а вот из `loop()` та же функция вызывается на реконнекте, и там
пятнадцать секунд встаёт всё: часы, секундомер, веб-сервер и опрос датчика.

Теперь это автомат: `wifiBeginConnect()` начинает ассоциацию,
`wifiConnectStep()` двигает её на шаг из `maintainNetwork()` и говорит, когда
закончилось. В `setup()` он же прокачивается на месте — там ждать можно, на
экране заставка, а `syncNTP()` следом без сети всё равно бессмысленна.

Вся работа «после связи» — `localIP`, режим радио, mDNS — собрана в
`wifiOnConnected()`. Это важнее, чем кажется: связь возвращается не только
через автомат, но и сама, авто-реконнектом стека. Раньше после такого возврата
`MDNS.begin()` не вызывался вовсе, и `clock.local` молчал до перезагрузки —
адрес по IP при этом работал, отчего симптом выглядел как проблема сети, а не
прошивки. Признак `wifiReady` отмечает, отработала ли эта функция для текущей
ассоциации; проверка связи раз в 10 с доводит до конца то, что поднялось мимо.

## Serial-монитор пуст

USB-C на C6-Zero подключён к **нативному USB Serial/JTAG**, а не к отдельной UART-микросхеме. Без флагов `Serial` уходит в UART0 (GPIO16/17), который к разъёму не подведён. В `platformio.ini` уже есть:

```ini
build_flags =
    -DARDUINO_USB_MODE=1
    -DARDUINO_USB_CDC_ON_BOOT=1
```

Правка `platformio.ini` **не меняет чип** — нужна пересборка и повторная заливка:

```bash
pio run -t clean && pio run -t upload
```

## `OSError: [Errno 71] Protocol error` при заливке

esptool пытается дёрнуть линию **RTS** для автосброса в download-режим, а нативный USB-JTAG этого не умеет. Решения:

1. Вручную: зажать **BOOT** → коротко нажать **RST** → отпустить **BOOT** → `pio run -t upload`
2. Или отключить автосброс:
   ```ini
   upload_flags =
       --before=no_reset
       --after=hard_reset
   ```

## `Could not open /dev/ttyS0`

Автоопределение порта промахнулось: `ttyS0` — это COM материнской платы. Плата — `/dev/ttyACM0`.

```bash
pio device list                                   # посмотреть реальный порт
pio run -t upload --upload-port /dev/ttyACM0
```

Или прописать в `platformio.ini`: `upload_port = /dev/ttyACM0`.
Порт занят или залип после неудачной заливки — **передёрни USB-кабель**, часто этого достаточно. Монитор при заливке должен быть закрыт: USB-CDC один на всё.

## `riscv32-esp-elf-g++: not found` (Error 127)

Проблема окружения, не кода:

- Тулчейн скачан частично → `rm -rf ~/.platformio/packages/toolchain-riscv32-esp* .pio && pio run`
- Сборка в **Alpine/musl** Docker → prebuilt-тулчейн собран под glibc и не запускается. Нужен Debian/Ubuntu-образ (например, `python:3.12-slim`).
